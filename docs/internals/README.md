# Internals

This page is for anyone who changes or extends the code with nothing but this repository at hand: the parts and where they live, how a table turns into a verdict, the rules the code keeps, each check with the command that runs it and what it should print, and what lives outside. The two shape crates have a page of their own, [Internals of the shape crates](shape-crates.md); this page gives their place among the other parts and their share of the checks. The user reference is the [reference](../reference.md); the method is in [parity](../parity.md). One internals page per unit joins these as units are rebuilt.

## From a table file to a verdict

1. `Table::parse` reads the predicted table: it skips blank lines and comment lines, requires the magic line `table v1` or `table v2`, and turns each row into a `ParamDef`. A value written in decimal (`f:`) is parsed into a float once, on load.
2. `pair_tables` takes the observed table, the parameters the original registered, as a `Table` too, so both sides are compared in one representation.
3. `pair_tables` claims rows with the same known id first (the key is reported), then exact name matches, in the predicted table's order, then normalized ones; an observed row is claimed at most once.
4. For each claimed pair, every field gets a verdict: the kind `Same` or `Differ`, and the id, name, default, minimum, maximum, flags, extra cell and the two host words `Same`, `Differ`, `Unscored` (the prediction is unknown) or `ObservedUnknown`. Differing flag sets also give `flag_diff`.
5. The `Pairing` holds one verdict per predicted row and the names of the observed rows no prediction claimed. The caller decides whether the pairing passes; the method's rule is that nothing stays unmatched on either side ([parity: the interface pairing](../parity.md#the-interface-pairing-and-calibration)).
6. `Table::serialize` writes a table back with every float as its exact bits (`b:`). Text that the serializer produced therefore comes back byte for byte after a parse and a second serialize. Text written by hand need not: the serializer drops comments and blank lines, turns `f:` cells into `b:` cells and writes integers and flags in a form of its own, so the text can change while every value read from it is kept. The test `serialized_table_round_trips_but_hand_written_text_does_not` checks the first statement on a table the serializer wrote, and the second on a hand-written table with a comment, a blank line and an `f:` cell.

## Rules the code keeps

These are the rules of `effect-params`. The rules of the shape crates are hypotheses about the original, and [their page](shape-crates.md#the-hypotheses) lists them together with the crates' own choices.

- **Unknown is not zero.** A cell that is `?` is `Cell::Unknown` and stays so; a prediction that is unknown is `Unscored`, never counted as a match or a difference.
- **Floats are compared as bits.** `Cell::bits_eq` compares floats by `to_bits`, so -0 and 0 differ and two NaNs are equal only when every bit is the same. Integers compare by value, and an integer cell never equals a float cell.
- **No rewriting before a comparison.** Neither table is changed to make a field compare; a decimal value is turned into bits once, when it is read, and never re-printed for a comparison.
- **One partner per row.** A predicted row gets at most one observed row and an observed row is claimed once, with exact names before normalized ones.
- **Flags as one set.** Flag sets are compared whole; `diff` and `flag_diff` give the bits that differ.
- **Nothing of the plug-in.** The code and the tests hold no name, value, default or flag of the original; every test name is invented, and the flag names are this crate's own.
- **No dependencies and no `unsafe`.** The crate uses the standard library only.

The original plug-in files, the Windows system libraries, the After Effects SDK and every layout made from it, the emulator harness with its register of host answers, the call records, the reference outputs, the predicted parameter tables, the specifications written from static reads of the original's code ([README: legal](../../README.md#legal)), and the cases of the shape data check with their predicted dumps ([reproduce: inputs you supply](../reproduce.md#what-needs-inputs-you-supply)). Nothing in the repository needs them to build or to pass its checks.

## Changing the code safely

- **The format.** `serialize` and `parse` must still round trip every bit, which `round_trip_keeps_every_bit` checks, and the serializer's own text must still come back unchanged, which `serialized_table_round_trips_but_hand_written_text_does_not` checks. The example on the reference page is read by `example_parses`, so a format change that the example no longer meets fails `cargo test` until the page is updated. A changed format should get a new magic line, so that a file of the old format is refused rather than misread.
- **The pairing.** A change to `normalize_name` or to the claiming order changes which rows pair. It should come with a test that fails on the old behaviour, and a pairing already reported against a sealed prediction keeps the rule it was scored under.
- **The status rule.** A change to `tools/status.py` changes what every generated page says. Run `python -I tools/test_status.py`, then `python -I tools/gen_docs.py`, then `--check` and `tools/check_docs.py`; a page that changes says what changed and why in the [parity log](../parity-log.md).
- **Names.** Every name in a test or a comment stays invented. A name of the plug-in enters the code only with the unit that needs it for its interface.
- **The shape crates.** A change to a rule of the shape model changes the predictions, and a change to the dump form changes every dump; [their page](shape-crates.md#changing-the-code-safely) says what such a change has to keep.
- **The mask sequence form.** `example_exact_bytes` holds the example manifest, built from two invented frames, and `reference_example_is_canonical` holds its copy on the reference page, so a change to the manifest, to the frame file or to the hash fails `cargo test` until the example and the page change with it. A changed form should get a new `format` value, so that a manifest of the old form is refused (`manifest_format`) rather than misread. The interface file follows the binary: a change to an exit code, a report line or a reason word fails `interface_contract.rs` until the file says the same.
- **The frame contract.** The three layouts and their sizes are the convention's, not this repository's, and `crates/stage-cli/src/frame.rs` repeats them: a change to one is a change to both, and only when the convention changes. A pattern of `frame-gen` must give the same bytes on every platform, so its arithmetic stays in integers or in exactly stated float operations; a new pattern comes with a test of its exact bytes.
- **The stage program.** The manifest must still validate against `contracts/stage-manifest.schema.json`, and the conformance command of the [checks](#checks), run from a twixtor checkout, must still pass. A stage that computes something of the plug-in is added only after its unit has been compared under the [parity](../parity.md) rules; `selftest-copy` stays a copy.
- **The five further generic crates.** A default of a configuration claims nothing, and the list of configurations of each crate is part of its interface: a new choice is a new field or a new variant, listed by the crate's enumeration, and the tests that count or pin the enumeration change with it. An existing configuration keeps its results, so that a configuration once selected by comparison still means the same thing. The arithmetic stays within the operations stated in the [reference](../reference.md#the-generic-crates), with no fused multiply add and no transcendental function of the platform's maths library.
- **`sphere-reorient`.** The series of `trig` are fixed in their number of terms; a change to them changes pinned bit patterns in the tests, which then change with it. Sine and cosine keep their symmetry for negative angles, which `audit_reorient.rs` checks.
- **`mesh-warp`.** Two triangles that share an edge must agree on the points of that edge, so that no point of the mesh falls between them; `audit.rs` checks it. A change to the tie rule or the locator keeps the order in which triangles are tried.
- **`blend-ops`.** The order of operations of `composite_pixel` is the stated one, and the guard values of dodge and burn stay fields of `Config`; `reference.rs` holds the modes to the published formulas.
- **`key-eval`.** Every solver does a fixed amount of work and never stops early on the data. The test that walks every configuration compares a pinned digest, so a change of any result changes the digest, which changes only with a stated reason.
- **`planar-track`.** Its tests hold tracking results within a stated tolerance of the truth, and single steps by exact equality. A change to an update rule keeps the order in which it composes its step, which `audit_kill.rs` checks, and a corrected pose is never extrapolated from the tracked pose before it.
- **The contracts.** `contracts/` is never edited here. A newer version is taken whole from twixtor, and the commit it was taken at is stated on the [handoff](../handoff.md) page and in the [reference](../reference.md#mocha-stage).
- **The generic crates.** Each of the seven keeps its choices in its `Config`, and a new choice is a new field that `enumerate` lists, with a test that two values of it give different results. A default stays a neutral starting value that claims nothing about any program; a value is changed to match a program only after a comparison with the original selects it, and the comparison, not the code, records why.
- **Arithmetic.** The seven crates use add, subtract, multiply, divide and compare in a fixed order, with no fused multiply add and no library transcendental function, so their results have the same bits on every platform. A change that adds a library call, a fused operation or a new order of summation changes bits, and its tests, which include pinned bit patterns, say so.
- **`pixel-format`.** `Config::parse` accepts only the text `canonical` writes, and every offset of a layout is checked and returns `LayoutError::Overflow`; a change keeps both. The integer premultiply stays exact in integers.
- **`contour-eval`.** The X-spline polynomials follow a public reference implementation and are checked against what the paper states; a change to one is tested against those statements and the vectors of `tests/vectors.rs`. The limit of 24 levels and a `Uniform` count above 4096 stay refusals; a `ByLength` count above 4096 segments is held at 4096, and a change keeps that as it is or documents the new rule.
- **`coverage-raster`.** Exact area stays exact for self intersecting input under both fill rules, and the sample methods keep the top left tie rule; the independent supersampling reference in `tests/reference.rs` is the check for a change.
- **`planar-xform`.** The four point solve keeps its pivot rule, the lowest row on a tie, because a different rule changes bits. A singular or non finite transform is an `Error`, never a silent value.
- **`resample`.** A tap of weight zero is skipped and the interpolating kernels return exact 1 and 0 at integer offsets, which keeps the identity mapping and the reach of a non finite sample as they are; the sinc series keeps its stated bound.
- **`lens-model`.** The iterative inverses run exactly the requested number of steps with no convergence test. The numbering of the two tangential terms is documented in the crate and pinned by a test.
- **`soft-edge`.** The exponential and the cosine profile are evaluated by the crate's own fixed series, not by a library call, and a size that does not fit the buffer is `SizeMismatch`, never a panic, except in `squared_distance_transform`, which asserts on a length that is not the width times the height.
